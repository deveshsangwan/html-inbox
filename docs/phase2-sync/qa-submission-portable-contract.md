## QA-R10: cancel this ticket when admission is uncertain

The actual worker admits a run ticket before its control acknowledgement reaches the CLI. SIGINT in that interval aborts the acknowledgement request, leaving the current acknowledgement-only flag false. Both cancellation sites then skip this CLI’s own running request. Verified HTTPS probes on Node 20 and 24 observed the request remain active with several seconds left; the same bounded exact-ticket cancellation API stopped it in 34–36 milliseconds. Remote bytes and custody remained intact. These are controlled interleavings, not a claim of natural incidence.

Keep the existing generated ticket ID, control operations, deadlines, best-effort error handling and at-most-once cancellation. Record that submission of this exact ticket was attempted immediately before dispatching the awaited run control call. Distinguish that fact from a received acknowledgement where error classification depends on the latter. Either cancellation site may cancel this exact attempted ticket after interruption despite an uncertain acknowledgement. A cancel for a ticket never admitted can safely return false.

Do not infer admission, successful delivery or acknowledgement from this new state. Do not change error classification for unrelated failures, pause or erase durable work, cancel other/background tickets, extend the foreground or 150-millisecond control bound, add a wire/store/worker schema, or undo remote custody. When no run submission was attempted, perform no ticket cancellation. Preserve the normalization after the final awaited cancellation and all previous early/late cancellation guards.

Before the fix, add an expected-correct actual retained CLI test holding exactly one real run acknowledgement after worker admission and one real active HTTPS response. Prove the ticket and request are active before SIGINT, the control channel is usable through a separate calibration, and sufficient deadline budget remains. The corrected CLI itself must issue the bounded own-ticket cancellation, abort the actual attempt and close the response before ordinary expiry. No test-side cancel may explain the passing case. Retain exact saved bytes, canonical receiver identity, real receipt, enabled/unpaused worker and queued-recovery assertions. Keep acknowledged, unavailable-channel, no-submission/local-only, no-signal and late-viewer/status controls.

## QA-R11: dispose the entire newly opened portable file lifetime

Portable acquisition opens an exclusive file, but its initial stat precedes guaranteed cleanup. A stat error leaks the actual descriptor while leaving an unknown empty lock. Its write/sync failure branch directly closes the file; a recoverable first-close error masks the primary failure and leaks a descriptor. The public portable ownership API and actual ordinary catalog creation reproduce these on Node 20 and 24. No protected callback, foreign unlink or data loss was observed. Unknown namespace retention is conservative authority, distinct from the descriptor defect.

Bring the whole lifetime after a successful exclusive open, including initial stat, under guaranteed disposal on acquisition failure. Reuse the existing `finishLockOperation` and `closeLockHandle` behavior to preserve primary, inspection/unlink and cleanup causes and apply the existing bounded close retry. Success still transfers the retained handle into the existing ownership object and preserves its release/disposal coordination.

Remove a name only when existing checked inode authority proves it belongs to this invocation. If initial inspection failed and cannot establish that authority, retain the uncertain name while closing the descriptor. Inspection, unlink or close failure must not skip other safe disposal or erase the original failure. Permanent close failure remains an explicit bounded error, never false cleanup success. Never enter protected work or return acquired ownership on incomplete acquisition.

Do not add managed directory fsync, platform rejection, force-unlink, age/PID guesses, general reclamation, relaxed metadata/hardlink rules or a new resource framework to portable catalog behavior. Its historical create-before-owner-write crash limitation remains. Managed atomic publication, general private-file/HTML checks, owner death proofs and flush ordering stay unchanged.

Required red/green tests use actual captured FileHandles and restored native fstat/EBADF checks. Cover initial stat failure; write and sync failure paired with one recoverable close rejection; compound inspection/unlink/close errors; ordinary successful acquire/release; and the actual `createInbox` registration caller. Assert exact injection hits, no acquired ownership, preserved causes, closed descriptors where the OS close succeeds, unchanged foreign paths and conservative unknown lock retention. A fixture’s later manual descriptor close is teardown only and cannot satisfy product cleanup assertions. Keep portable platform and unavailable-directory-fsync controls.
