# Protocol integration contract

Frozen before the protocol writer starts. This addendum makes the exchanges in `architecture.md` concrete against the implemented storage interface. It preserves the approved proposal and all six acceptance groups. The read-only design task was `phase2-protocol-state-machine-20261024-a`; its findings below are accepted for implementation. Storage-only tests do not prove these wire semantics.

## Authentication and limits

Every protected request supplies a scoped credential plus a bounded binding with protocol version 1, route ID/revision, caller peer ID, target peer ID, source inbox UUID and destination inbox UUID. Resolve the route locally, compare credentials with timing-safe comparison, and check peer/target/direction/revision/operation/origin scope before consuming report payloads or disclosing report existence. Return a uniform non-disclosing authorization failure. Construct `RouteAuthorization` from trusted local configuration; the two endpoints have different immediate-peer IDs. No wire field selects a local path.

Use verified HTTPS with normal hostname/CA verification, explicit private CA support, no plaintext, redirects, certificate bypass or automatic LAN/tailnet trust. Ingestion is separate from reader and local process control. Header ceiling 16 KiB, URL 2 KiB, descriptor 64 KiB, HTML 10 MiB, page/holdings batch 128 entries, complete inventory 10,000 descriptors/64 MiB. Bound all envelope sizes, session/transfer counts, concurrent requests and staged bytes. Identity JSON is at most 4 KiB; offer/receipt 66 KiB; readiness 2 MiB; manifest page 16 MiB; holdings response 32 MiB. Reject unknown fields and compression. Opaque nonces/tokens use bounded base64url encoding of cryptographic random bytes.

Initial resource settings are at most 8 sessions, 128 MiB of cached cuts, 4 concurrent inbound transfers, and 16 staging reservations totaling at most 64 MiB. Reserve expected byte length under the shared store lock before transfer so concurrent or crashed attempts cannot bypass the total budget. Release failed/unused owned stages on normal exit. Crash cleanup requires conclusive lease-owner death and the shared lock; age alone never removes an active stage. Quota exhaustion is a persistent visible blocked/error result. Never delete a referenced or uncertain final body merely to free staging space. General retained-body/orphan reclamation remains separately deferred as recorded in the storage interface.

Default absolute network request deadline is 5 seconds, including DNS, connect/TLS, headers and response consumption. A manifest cut expires after 60 seconds. A multi-request catch-up pass also has a finite total bound. The normal foreground publication deadline remains 30 seconds overall, configurable within finite validated limits. A request or session timeout never discards its durable obligation.

## Fixed endpoints

`POST /sync/v1/identity` takes `{nonce}` generated by its caller. It returns `sessionId`, echoed `requestNonce`, responder-generated `challengeNonce`, `peerId`, `inboxId`, `storageIncarnation`, `scopeDigest` and `expiresAt`. Bind the session to both identities, route/revision, source/destination, exact approved scope and storage incarnations. This endpoint validates existing authorization; it does not pair peers.

`POST /sync/v1/manifest` accepts exactly one of `{op:"pull",sessionId,cursor}`, `{op:"push",sessionId,page}` or `{op:"ready",sessionId,ready}`. A page contains `evidence: CompleteInventory`, page number, at most 128 `OriginState` descriptors and an opaque next cursor or null. Completion evidence names the source peer and includes the receiver's fresh nonce. The evidence stays identical across the cut. Push returns continue or a terminal-inventory readiness ACK; ready submission returns active.

`POST /sync/v1/holdings` takes a bounded ordered identity list. It returns storage incarnation and matching current signed state/null, body availability, suppression and at most one relevant historical receipt per identity. Obtain incarnation, state, membership, availability and receipts from one coherent store snapshot. Availability is separate from historical custody. These responses must not expose an unflushed receipt written by another process: acquire the shared writer lock, establish durability for the validated visible snapshot and directories, then build the result from that same cut. This requires metadata/directory flushes, never routine HTML opens. Test an already-running reader while another process fails its ledger-directory fsync.

`POST /sync/v1/offer` takes `{descriptor}` and calls the common store apply operation without bytes. A needs-body response contains a transfer ID and expiry bound to route/revision, target and exact descriptor. Valid tombstones remain acceptable during incomplete live reconciliation. Other responses carry the store's durable disposition/receipt.

`PUT /sync/v1/body?transferId=...` sends original octets with the authenticated descriptor's exact Content-Length. Count/hash bounded actual chunks through `applyStream`, recheck authorization and current origin state under the commit lock, and reply only after durability.

`GET /sync/v1/body?sessionId=...&originInboxId=...&originDocumentId=...&fingerprint=...` pins an authorized current body under the store lock and checks the expected fingerprint there. Return exact original octets and length, or an authenticated unavailable/state-changed result. Do not silently substitute a newer descriptor.

Successful JSON responses use 200. A 202, offer acceptance, transfer ID, body-exists answer or readiness ACK is never body custody. Expired session is 410, history/state conflict 409, limits 413 and temporary unavailability a bounded 503. Authentication precedes protected error detail. Exact validated durable receipts and their disposition determine delivery, not status code alone.

## Shared history handshake

All new and revised routes start reconnecting, including a new route ID for retained canonical records. No route-ID change bypasses tombstone-first reconciliation. Metadata exchange is permitted; live body forwarding remains fenced. Removed/detached routes permit no communication, including terminal-only traffic.

For source-initiated push A→B, A sends nonce N_A to B's identity endpoint; B returns fresh N_B. After receiving N_B, A captures one current immutable inventory cut and posts its pages to B. B applies independently verified tombstones as pages arrive without claiming completeness. Once every page, signature, scope/epoch, count and ordered digest validates, B calls inbound `completeInventory` with its locally held N_B. It then returns `{kind:"terminal-inventory-ready",evidence,ackNonce:N_A,receiverPeerId,destinationInboxId,storageIncarnation}`. A validates this against its retained issued cut and pending N_A, then activates its outbound revision through a separate locked operation. A can now offer and PUT actual payloads. B never needs a callback to A's listener.

For independent pull, B sends N_B to A's identity endpoint; A returns N_A. B fetches pages from the cut A captured after receiving N_B. B runs exactly the same tombstone validation and inbound completion, then submits the readiness ACK to A. A activates outbound delivery. B first applies each live descriptor without bytes, then fetches only missing bodies and calls the same `applyStream` used by push. Its durable item receipts remain discoverable through holdings/offers.

Never use `evidence.nonce` as its own expected proof. Expected nonces come from locally pending sessions. Keep the captured cut for at most 60 seconds, with strict page order and unique canonical keys in locale-independent order. Even an empty cut has a final page. Expiry/lost session state requires a fresh challenge and cut, never repackaging a cached checkpoint. Concurrent later mutations are subsequent reconciliation work.

The readiness ACK proves application of terminal history. It is neither body custody nor completion of live transfer. `completeInventory` becomes inbound-only. Add narrow outbound activation that validates the authenticated ACK, issued cut and fresh challenge under the mutation lock. It must not call inbound apply, create inbound contributions, fabricate local custody receipts or store an inbound complete-inventory checkpoint for an outbound route.

Distinguish the trusted terminal-history cut from a fully reconciled pull checkpoint. Applying every metadata page can establish history readiness while live bodies are still absent. Add a separate locked completion operation/checkpoint that advances only after every item in that cut has a recoverable applicable outcome: live body plus membership, explicit local suppression, or a dominating terminal state. Missing bodies keep that full checkpoint incomplete. An individual item receipt never advances it. Expose the two meanings separately in status, and test that receiving item 100 cannot claim item 99 arrived, even after the manifest pages were enumerated. A stale cut cannot roll back either record state or a newer completed checkpoint.

## Required store integration corrections

Keep durable obligations for reconnecting routes. Live work stays visibly history-blocked; verified authorized terminal state can travel while history is incomplete. Detached/revoked work is retired and silent. Once origin-level complete history is trusted, retained verified tombstones belong in a complete relay cut even when their contribution was detached while that tombstone was applied. No attached live membership is needed to preserve deletion history.

Current holdings reconciliation runs on startup/wake/reconnect and periodically for every active outbound route, even with an empty pending queue or physically cleaned completed outbox. Missing acknowledged bodies create durable repair obligations. Repeated observations preserve attempts/backoff/errors/blocked state and do not act as explicit retry. Suppression is a distinct disposition. Incarnation changes require fresh receipt/membership reconciliation even when bytes remain available. A stale-incarnation receipt cannot retire current repair.

A superseded response may contain a valid newer owner tombstone. Add a narrow state-only observation operation for an already authorized outbound canonical record. Verify the origin signature and immutable descriptor, merge terminal state and derive onward obligations without inventing incoming membership or owner events. Unexpected state ahead of local owner history fences owner recovery. Do not simply acknowledge a fingerprint different from the queued state or repeatedly resend the stale live state.

Before every local request start, including probes/history/holdings/retries, authorize and synchronously construct the request while holding the shared store lock. A prior lockless snapshot is insufficient. Release the lock before network waiting. Register attempt cancellation by route/revision; local revocation invalidates sessions/transfers and aborts active work where possible. A completed remote commit remains a completed remote commit. Incoming body finalization keeps its existing locked revision, identity and tombstone checks.

Retain exact signed origin identity/metadata across relay. Only explicit origin/epoch/key, immediate-peer, destination, redistribution and complete-history scopes are trusted. A relay's complete cut describes its authorized durable view, not an unreachable origin's unknown later events. Canonical uniqueness and per-route receipts terminate duplicate forwarding and cycles. Item receipts never advance complete inventory checkpoints.

## Verification gate

Use the actual application HTTPS handlers/client and real stores in loopback multiprocess fixtures. Prove push when the source listener is unavailable, independent pull repair, both initial and fresh-revision terminal handshakes, new route-ID retained-copy fencing, coherent generation pagination, wrong TLS/auth/scope rejection before disclosure, lost ACK and simultaneous push/pull, current holdings with an empty queue, idempotent blocked repair, incarnation change, receiver-local revoke/target replacement during transfer, relay tombstones and cycles. Add the cross-process failed-flush custody-read case above. Preserve original reader/CSP/sandbox/export behavior. These protocol tests precede worker/CLI subprocess acceptance; neither substitutes for the other.
