1. HIGH — Successful worker close releases lifetime authority before inbound mutations settle.

Locations: packages/cli/src/sync-worker.ts:411-425 and :433-439; necessary surrounding implementation packages/cli/src/sync-http-server.ts:369-372 and :519-529.

The worker awaits ingestion.close(), then its outbound drain, and removes the runtime record/releases the lifetime lock. Ingestion.close() clears sessions/transfers, destroys sockets and awaits server.close(). That waits for the listener/connections; it does not wait for asynchronous request handlers already inside store operations. Destroying a response socket does not cancel a validated inbound offer's pending apply. The worker's draining variable covers its own outgoing pass, not incoming mutations.

Independent evidence: inbound-drain.cjs enrolls two real synthetic stores, configures a real receiver worker and explicit routes, and confirms the first publication over verified loopback HTTPS. After the source signs a deletion, the probe holds only the receiver's existing ManagedSyncStore.apply seam immediately before invoking its real implementation for that terminal offer. No fake receipt or invented terminal state is used. While this authenticated request is pending, worker.close() resolves, its runtime record and lifetime lock disappear, and both exact listener ports can be rebound. The receiver is still live and activeRequests is 1. Releasing the bounded gate then runs the real apply; the receiver becomes deleted AFTER successful close. Both runtimes exhibit precisely this sequence. Expected-correct assertions fail on both, exit 1. Logs: node24-inbound-drain.log and node20-inbound-drain.log; exact argv/environment/results: inbound-commands.json.

This is a controlled request interleaving, not a claim about a naturally observed slow physical disk. The post-close mutation and released lifetime authority are observed. A successor could now acquire the released authority while old accepted work remains; that overlap is an implication of the observed state, not a separately started-successor experiment. No unauthorized report disclosure, lost report or forged receipt was demonstrated.

The fatal-worker gate expressly requires settling replication before releasing lifetime ownership. It is broader than the old read-only late-pin response fix. This finding concerns a real mutating inbound terminal offer; it does not reopen the accepted R10 rule allowing an observed late read-only pin to clean itself up without late output. The source gap partly predates the new correction, but the correction's full shutdown guarantee remains unsatisfied.

Recommended correction: make ingestion shutdown account for in-flight mutating work, and keep worker ownership until that work has settled or shutdown has rejected while retaining authority. Stop new admission, close/abort transport as appropriate, and observe every already-started operation. A socket-close event must not stand for mutation completion. Do not roll back a completed receiver commit. Use a small server-owned collection/counter of actual handler promises or equivalent existing lifecycle mechanism; no generic job framework or second storage authority is needed. Require the held-real-terminal regression to keep close pending and ownership present until the mutation settles, then prove no post-close mutation. Cover body ingestion and fatal-triggered shutdown as well as ordinary close.

2. MEDIUM — Failed worker cleanup abandons live ownership file descriptors.

Location: packages/cli/src/sync-worker.ts:431-444, especially :435 before :439. Retained handles originate in packages/cli/src/sync-files.ts:253 and :274; the only returned cleanup closes them at :308-318.

Retaining uncertain ownership names is correct. However, a listener/drain rejection skips ownership.release entirely, and a runtime-record read/removal rejection exits before that release. The new managed ownership object retains both its checked directory handle and its canonical-lock inode handle. There is no non-unlinking disposal path. The cached rejected closing promise prevents a later close call from attempting further cleanup, so reusable-library processes retain descriptors until garbage collection/process exit.

Independent evidence: cleanup-probe.cjs retained-handles wraps actual fs.open only for its synthetic root, starts a real temporary owned worker, then makes readWorkerRecordOffline reject during explicit close. Close rejects with the exact original error and notifies once. The control port rebinds, and runtime/lock names remain, as intended. But two actual FileHandle objects still have valid descriptors: the worker directory and the candidate-opened handle for the installed lifetime-lock inode. Repeated close returns the same rejected promise. Expected-correct zero-live-handle assertions fail on both runtimes, exit 1. The probe then explicitly closes those two handles without unlinking authority through product code and removes only its own synthetic home. Logs: node24-retained-handles.log and node_modules-retained-handles.log (the latter is the Node20 log despite its filename); receipts: probe-commands.json.

This establishes the resource objection with individual real descriptor attribution. It does not retroactively attribute every warning in the author's earlier runs. The old implementation also had related cleanup structure; this is an unresolved interaction between the new retained ownership handles and the promised independent fatal cleanup, not an unsupported claim about when every leak first appeared. Impact is retained descriptors and GC-dependent cleanup in reusable long-lived processes, not demonstrated unsafe lock reclamation.

Recommended correction: separate namespace release from handle disposal narrowly within the ownership implementation. Failed shutdown must preserve uncertain lock/runtime names while still attempting independent descriptor cleanup and preserving any cleanup failures. Do not simply call normal release after a failed drain, because that would remove authority while work might still act. Add actual FileHandle accounting to record-read/removal and listener/drain failure tests. Assert that names remain when required, handles are closed once safe, explicit close still rejects, and later calls do not silently claim successful cleanup.

3. MEDIUM — Early startup-exclusion cleanup failure bypasses fatal notification and masks the startup cause.

Location: packages/cli/src/sync-worker.ts:68-79. The once-only fatal state/handler is established later at :90 and :161-174. The later startup catch at :147-154 has the intended aggregation and independent cleanup, but does not cover this earlier acquisition block.

If inspectWorkerOwner or lifetime acquisition rejects, the catch awaits startupExclusion.release before rethrowing the original error. If that release rejects, the cleanup error replaces the original and onFatalStop is never called. This is an unexpected cleanup failure before readiness, not a normal failed admission whose cleanup succeeded. The new CLI installs its handler before start, but never receives this notification and therefore takes its ordinary error-reporting path.

Independent evidence: cleanup-probe.cjs early-cleanup creates a real malformed private runtime record and obtains the actual startup exclusion. Its wrapper performs the real release, then rejects with a marked synthetic cleanup failure. On both runtimes: one release, zero notifications, returned plain Error equal to the cleanup failure, original SyntaxError absent, and no remaining handles. Expected-correct notification/cause assertions fail, exit 1. No listener started. Logs: node24-early-cleanup.log and node_modules-early-cleanup.log; receipts: probe-commands.json.

The release failure is deliberately injected after the actual operation, representing the already recognized performed-then-rejected class. Missing notification and original-cause loss are observed. Raw CLI reporting follows from the inspected catch and handler code; I did not run an additional CLI subprocess for this case or claim an actual secret disclosure.

Recommended correction: establish the no-payload once-only notifier early enough to handle this cleanup path, and aggregate the original acquisition/inspection error with the cleanup failure. Preserve ordinary pre-start validation/admission errors when cleanup succeeds. Do not call the current fatalStop closure before its later initialized shutdown state exists. A small early-safe notification function plus the existing shutdown code is sufficient. Add the malformed-runtime plus failed-exclusion-release regression, including throwing/rejecting observers, original causes and exact sanitized CLI behavior before readiness.

4. MEDIUM — Reaper snapshot catch-all discards compound errors and permits the protected callback.

Locations: packages/cli/src/sync-files.ts:564 and :593. Related corrected aggregation is at :499-506.

lockSnapshot now correctly retains its original read/inspection error together with a required close error. Both reaper callers immediately turn ANY snapshot rejection into null. This is treated as unknown/absent ownership and ordinary contention is retried. A transient injected compound failure disappears; a later snapshot succeeds and the same acquisition enters protected work. The public readSyncOwnership unknown/null contract does not require these internal acquisition paths to swallow required-operation and cleanup failures.

Independent evidence: reaper-probe.cjs seeds a valid private v2 lock for a conclusively dead PID and calls public withStoreLock. It injects actual FileHandle.read EIO plus first-close rejection into either the original death-precheck snapshot or the snapshot under the .reap guard. The second close actually succeeds. All four expected-correct invocations fail, exit 1. Logs node24-reaper-1.log, node24-reaper-2.log, node20-reaper-1.log and node20-reaper-2.log; receipts reaper-commands.json.

This is a proven error-preservation/acquisition-result defect under controlled I/O failures. Subsequent fresh evidence may make the later reclamation safe; I found no foreign unlink or data loss in these probes. Successful later cleanup nevertheless does not meet the frozen compound-error gate, which explicitly requires both causes to survive and close-only failures to reject acquisition. The new twelve cases cover other repeated ownership operations but miss these two acquisition consumers of the new AggregateError.

Recommended correction: distinguish intentionally unavailable/unverifiable ownership from I/O/required-cleanup errors at these internal call sites. Preserve and propagate the latter through acquisition, while keeping malformed/unknown/live owners non-authoritative and untouched and preserving readSyncOwnership's public null behavior. Do not add blind retry, an age rule or force unlink. Add both existing-lock regression boundaries; a separate later explicit acquisition may recover normally after the original error is reported.
