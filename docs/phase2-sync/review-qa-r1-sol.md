1. Medium: retaining uncertain lock names also leaks the lifetime file and directory descriptors.

Exact location: packages/cli/src/sync-worker.ts:433, including the ownership-release branch at :439. Related ownership implementation: packages/cli/src/sync-files.ts:313, whose release closure owns both the retained read-only file and checked parent directory handles. Existing regression coverage: packages/cli/src/sync-worker-fatal.test.ts, the explicit record-cleanup rejection and listener-cleanup rejection cases.

Trigger: close() successfully stops scheduling, closes the control listener and settles its drain, then readWorkerRecordOffline rejects while deciding whether it can remove the worker record. Alternatively, an earlier listener/drain cleanup rejects. The worker correctly retains uncertain runtime/lock names, latches fatal state and rejects explicit close. However, every path that skips or fails before ownership.release() also skips the only operations that close those two retained handles. The stable rejected closing promise prevents a later close() call from attempting resource disposal.

Observed on Node24.19.0 and Node20.20.2 with the existing compiled production modules. resource-probe.cjs starts a real temporary owned worker in a fresh synthetic home, intercepts actual fs.open handles without changing their results, and injects only the record-reader cleanup failure. After close rejects, actual FileHandle.stat() still succeeds on both the worker directory and the regular single-link lifetime inode. The attributed Node24 run retains descriptors 23 and 24; Node20 retains descriptors 20 and 21. Notification is exactly once, the control port is already closed and can be rebound, and the canonical lifetime owner remains the current worker token. The expected-correct zero-open-handle assertion fails on both runtimes. No handle-close syscall is injected or made to fail.

Impact: reusable-library callers can retain OS descriptors after a settled shutdown failure. Multiple failed workers in a long-lived host can accumulate descriptors and rely on GC or whole-process exit for disposal. The ordinary standalone CLI's process exit will let the OS reclaim them, so this is not evidence that the demonstrated CLI continues serving after exit. It is a resource-lifecycle defect in the explicitly reusable library contract. This independently attributes a concrete leak mechanism; it does not retrospectively identify every descriptor in the author's uninstrumented GC warnings.

Recommended correction: separate disposal of the held file/directory handles from removal of their authority names. Add a narrow internal ownership-disposal operation that closes handles while retaining canonical/candidate/guard evidence, and invoke it on failed shutdown as well as successful release. Preserve once-only fatal notification, explicit close rejection and every original cleanup cause. Do not call normal release when authority is uncertain or force-unlink the lock. Regression tests should inspect actual handle closure after listener and record-cleanup failures, assert that retained names/owner bytes are unchanged and still prevent another live owner, and retain the ordinary successful-close control. Fixing this requires no storage-authority rewrite or generic resource framework.

Evidence: resource-node24-attributed.json, resource-node20-attributed.json and resource-probe.cjs in this report directory. Each final attributed probe exits 1 because the expected-correct resource assertion is unmet. Its finally block then explicitly closes both intercepted handles, rebinds the exact control port and removes only its own fixture.

2. Medium: early startup-exclusion cleanup bypasses the fatal notifier and masks the acquisition error.

Exact location: packages/cli/src/sync-worker.ts:77, especially :78. Compare the later startup catch at :147, which aggregates the original and cleanup errors, and the late startup-exclusion release at :143, which invokes fatalStop. The fatal latch is initialized only at :90. CLI consequences follow through sync-cli.ts:215 and :289, whose catch rethrows when the callback has not set fatal.stopped.

Trigger: lifetime ownership acquisition or its owner preflight fails after the startup exclusion was acquired, then releasing that startup exclusion also fails. This earlier catch awaits release directly and throws the acquisition error only if release succeeds. Consequently the cleanup rejection replaces the original error, and onFatalStop is never called. This gap is outside the later try/catch added by this correction.

Observed on both runtimes through actual filesystem-operation seams in startup-syscall-probe.cjs. The probe injects one EIO into the real lifetime candidate's writeFile and one EIO into the real retained startup-parent handle's sync after the startup lock has actually been unlinked. Each run records candidateWriteFaults=1, startupReleaseSyncFaults=1, notifications=0, originalErrorRetained=false and cleanupErrorRetained=true. The only returned cause is the startup directory-sync error. All acquired handles are actually closed and no listener/runtime readiness is reached. An earlier function-seam probe independently observes the same ordering; both versions are retained.

Impact: callers using the new callback receive no fatal-cleanup notification for this startup branch, and lose the error that caused startup to fail. At the CLI, the callback-dependent sanitized fatal path is bypassed; the outer CLI catch will print the original cleanup error message rather than the fixed diagnostic. That CLI diagnostic consequence is source inference, not a separately launched CLI experiment. Exit 1 already occurs through the ordinary startup-error path, so this finding does not claim a false exit 0 or false readiness. It violates the new gate's once-only cleanup notification and error-preservation behavior before readiness.

Recommended correction: establish the once-only notifier before the early acquisition catch, or include this acquisition/exclusion lifetime in the same small startup cleanup path. If release fails, notify once and retain both acquisition and cleanup errors in an AggregateError. An ordinary preflight/acquisition failure with successful cleanup should keep its normal startup-error behavior. Add this exact early write-EIO plus release-sync-EIO ordering, a cleanup-only case and a successful-cleanup control. Do not turn routine not-ready/preflight rejection into an automatic fatal callback.

Evidence: startup-syscall-node24.json, startup-syscall-node20.json and startup-syscall-probe.cjs. Both expected-correct probes exit 1 at notifications=0. No syscall-close failure, arbitrary process signal, foreign path or unsafe lock removal is involved.
