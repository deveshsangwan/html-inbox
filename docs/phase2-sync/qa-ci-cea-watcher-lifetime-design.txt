Recommendation

Use one awaitable close operation on the real route-attempt module. Keep its public result inline and purpose-specific:

Promise<{ signal: AbortSignal; close: () => Promise<void> }>

close() must synchronously stop admission of further watcher checks and return one stable promise joining the already-admitted check through its real lock operation and cleanup. Retain the active-attempt registry entry and parent abort listener until that check settles. Every actual production owner must await close. This fixes lifetime at the module's own interface rather than exposing private methods to fixtures.

An unconditional await of the present10s watcher is not the smallest complete correction under the existing transport contracts. A source watcher can be queued behind the same real store lock whose release the existing late-pin test intentionally postpones until after response termination and attempt quiescence. Waiting for that watcher without cancelling its queue wait would turn an allowed detached read-only pin into a blocked HTTP handler. The existing1000ms server-close and600ms attempt-quiescence assertions must not be widened. The complete candidate therefore also needs cancellation of this watcher's not-yet-acquired store-lock work, while joining all actual cleanup. This is a static allowed-schedule counterexample, not a newly executed failing test.

The recommended candidate touches five production files: sync-store.ts, sync-files.ts, sync-client.ts, sync-reconciliation.ts and sync-http-server.ts. Required close invariants

1. Open permits at most one admitted watcher check. The native50ms interval and its unref behavior remain. The interval callback checks an explicit closing/closed flag before admission, as well as the existing signal and in-flight guards. clearInterval alone is not the guard against an already-dispatched callback.
2. Admit and retain the entire check promise before it can enter its first asynchronous store operation. A promise assigned before a microtask invokes the real check is a small implementation option; this adds one microtask and is a scheduling change, not zero overhead. Do not retain only its eventual withStoreLock promise after checkDirectory has already yielded. Do not track only the authorization callback, which precedes ownership.release cleanup.
3. First close marks admission closed synchronously and clears the timer synchronously. Cache its returned promise before cancellation can synchronously invoke a reentrant observer. Cancel only this attempt's private watcher controller. This normal stop must not abort the public attempt signal or turn a successful request into cancellation.
4. Capture the admitted check, including a scheduled-but-not-started check. Join its complete observed promise. A callback delivered after the closed flag must make no new check or filesystem call. An admitted callback may either retire through the exact private cancellation path before acquisition, or finish its already-started operation and cleanup.
5. Keep the activeAttempts entry and parent listener until settlement. A concurrent parent abort or invalidateAttempts during the drain can still abort the public attempt; quiesceRoute cannot mistake a draining watcher for absence. Remove the entry/listener after the producer settles, including an already-observed failure. This registry is a lifetime set, not merely a timer-admission set.
6. Every concurrent or later close returns the same Promise object and same outcome. Use a cached non-async close function returning that promise; an async wrapper would produce a distinct wrapper promise on each call. No second timer clear, new watcher, new ownership attempt or cleanup retry is introduced.

No interval or close handle is invented for failed admission. No changes to authorization, deadline error classes or credential resolution at initial admission.

Why not remove registry/listener immediately

Caller awaits can protect one caller's return, but other users of the module do not observe that local promise. quiesceRoute observes activeAttempts. Removing an entry before its queued/acquired check settles would preserve the same false-empty observation at that interface. Detaching the parent listener before a new drain await also misses parent cancellation during that await. Keeping both until settlement is the smaller coherent contract. The synchronous guarantee belongs to stopping admission; registry removal is a completion event.

Registry emptiness does not promise every store lock name was successfully released, or every independent store operation has stopped. A check can settle with a storage failure, and detached read-only pins remain explicitly outside this watcher lifetime. Quiesce must still fail its existing bound if a relevant check cannot settle; it must not erase the entry to report success.

Error-policy recommendation and its exact limit

Today's watcher intentionally observes this.mutate rejection with catch(abort); abort creates the generic public attempt-aborted signal. It does not reject a retained watcher result to callers and does not currently preserve the original producer error as a public cause. That is existing classification, not an unhandled rejection.

For this lifetime gate, retain that classification: after excluding only the exact private normal-close reason, ordinary authorization/revocation/pause and storage watcher rejections still take the existing observed abort path. close joins that already-observed chain. It reports settlement, not a new guarantee that every underlying lock release succeeded. The existing generic signal remains the public watcher-error indication. Do not claim that original raw errors now escape through close, and do not add a new broad catch that discards failures from the join.

Underlying withStoreLock/acquireSyncOwnership/finishLockOperation must still construct and preserve their exact original errors and compound causes, without a new retry or error replacement. Dedicated negative tests should capture their real rejection at the existing exported operation seam, assert both causes and namespace evidence, and separately assert the existing public watcher abort classification. A compound failure must not disappear down the new private-close cancellation exception. This proposal does not make the existing generic abort channel a full raw-error reporting channel.

There is a real separate policy choice here. If the parent requires operational watcher errors, especially release/fsync/descriptor errors, to reject close with their original causes, that is a stronger contract and needs an explicit expanded gate. Blindly awaiting the raw rejected check would promote expected route revocation to a cleanup exception. Blindly throwing from three finally blocks can mask an existing request/route failure or displace a valid network result. A correct stronger policy would need to distinguish an expected fence error at the actual authorization callback from outside storage errors, preserve operation-plus-close failures, and audit the worker's per-route catch, which currently converts done rejection into ticket.error and may allow draining to resolve. Fatal ownership-cleanup propagation could therefore require sync-worker.ts and a production error distinction as well. Do not smuggle that change into the Promise<void> type update. Recommendation is to preserve existing abort classification in this gate and retain this raw-error visibility limitation explicitly for parent triage.

Deadlocks and bounds

There is no existing production call to close inside this attempt's watcher callback or a still-held mutation-lock callback: all three actual finalizers follow awaited store operations whose existing withStoreLock has already performed release. startCommunication returns a boxed value so network waiting happens after its mutation lock is released. Preserve that fact.

The module cannot promise reentrant awaited close from its own producer. That would wait for itself. Nor should a caller await close while holding a lock on which an already-acquired producer's completion depends. The safe pattern in a protected callback is to initiate the synchronous stop, retain the returned close promise, return/release the protected operation, and await the close promise outside it. Do not add an AsyncLocalStorage lock-ownership framework or a test-only self-detection export. The watcher's own callback must never call/await its close. Queue cancellation removes the ordinary queued-behind-my-holder cycle, but is not a universal self-await proof.

The10s default store limit is an acquisition bound, not a hard bound on arbitrary native I/O plus all cleanup. Alternatives considered

- Synchronous close plus settled/drain property adds ordering knowledge to every caller: close must precede await, and the property must mean the whole admitted lifetime rather than whichever check happened to be current. - Race close against a timeout/cancel event while leaving the original mutate queued is directly incompatible with the accepted203 mechanism. A later canonical writer would remain. Returning early is not cancellation.
- Changing the watcher to a lockless snapshot check could remove its canonical-lock production and its queue contention.
