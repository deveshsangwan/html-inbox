There are four High functional blockers. The fifth item is a Medium maintainability assessment, distinguished from runtime defects.

1. High: catalog transition recovery permits identity mutation before re-establishing durable intent.

Primary location: packages/cli/src/inbox-catalog.ts:388, especially the existing-journal branch through line 411 and the operation callback at line 431. Related implementation: sync-files.ts:111 and sync-maintenance.ts:30.

Trigger: replaceLedger successfully renames identity-transition.json but catalog-directory fsync fails. The operator retries the same explicit fork. The existing journal is parsed and its binding checked, but neither the journal nor its directory is flushed before the fork callback can durably change the owner ledger and then reader identity.

Observed evidence: catalog-repro.cjs intercepts the actual fs.open FileHandle.sync boundary. One EIO is injected at the catalog directory, after the initial journal rename. On retry, the fixture records all sync calls and stops immediately after successful sync of the directory containing the new fork ledger. The new ledger identity has become durable; the reader and registered catalog still contain the old identity. There were 24 sync calls on retry and ZERO syncs of the journal or catalog directory before this durable identity mutation. This directly answers the coordinator's open question: recovery does not establish the catalog-journal baseline that ManagedSyncStore.recoverLocked/baseline establishes for its own ledger.

The fixture then explicitly removes the unflushed journal to simulate its permitted loss after power failure. Retrying with the old expected UUID fails with 'Offline expected inbox identity differs from the ledger or recorded fork transition', and the catalog still has the old UUID. The ordering defect is observed. Loss of the unflushed entry is simulated, not a physical power-loss experiment.

Impact: a registered library can be stranded between durable new owner identity and old catalog/reader identity without the recorded old-to-new transition needed by the supported retry path. This violates the recoverable explicit catalog transition contract. It is an availability/recovery failure; I did not observe silent report deletion.

Correction: while holding catalog registration exclusion, validate and durably flush an existing journal and its containing directory before invoking any identity-changing callback. Reuse a small durable-intent recovery operation that treats uncertain rename/fsync outcomes as requiring a baseline, rather than treating successful parsing as durability. Retain the intent on any failure. Add actual EIO/ENOSPC before-directory-flush cases followed by retry and a cut after durable new-owner ledger commit. Existing identity tests cut only after successful directory flush.

2. High: successful sessions exhaust the receiver and permanently block normal replication.

Primary location: packages/cli/src/sync-http-server.ts:237. Session retention is at lines 80-84 and 311-316. Permanent classification is in sync-client.ts:157 and sync-reconciliation.ts:413; worker persistence/skip is in sync-worker.ts:261 and :289.

Trigger: eight successful reconciliation sessions reach the same ingestion server within the default 60-second lease. Every pass starts a new identity session. Completed push sessions retain all session state until expiry, and there is no normal completion/release operation. The ninth identity request hits the global eight-session limit and returns HTTP 413.

Observed evidence: session-repro.cjs uses two real ManagedSyncStore instances, the production reconciler/client and production HTTPS ingestion on an ephemeral 127.0.0.1 port, with a generated trusted CA. It publishes and reconciles nine small originals sequentially. Passes 1-8 confirm one transferred body each, with session count growing from 1 to 8. Pass 9 returns status='blocked', lastError='remote-rejected', blocked=1, transferred=0; the receiver still has only eight documents. No concurrency or hostile peer is required.

The worker consequences follow directly from current code: HTTP 413 is permanent, the blocked pass is persisted to routeRetries, and the scheduler skips blocked routes even after session expiry. The allowed 1-second reconciliation interval can also hit this through healthy idle polling. New publications, pull repair and deletion forwarding over that route then need explicit operator retry. The ninth-pass block was reproduced; that exact burst was not repeated inside a separate detached worker.

Correction: release completed push sessions, provide a bounded completion/release lifecycle for pull sessions, or safely reuse sessions with explicit challenge freshness. Preserve limits for genuinely active work. Treat temporary admission pressure as retryable with bounded delay rather than a permanent resource-limit error. Add more than eight successful passes/publications in one lease, multiple routes sharing one listener, 1-second periodic operation, and automatic recovery after admission pressure. The existing quota test checks eight unfinished identity sessions, while the unchanged-work test stops after five additional passes.

3. High: managed enrollment breaks administrator-owned viewer service operations.

Primary location: packages/cli/src/viewer-service.ts:48, with the same issue at :87 and :122. Also viewer-service-status.ts:33 and raw-home selection in inbox-selection.ts:109. The rejecting ownership rule is sync-files.ts:152-155, reached through ManagedSyncStore.isEnrolled and assertManagedLifecycle.

Trigger: a normal user owns an enrolled library and an administrator invokes the existing viewer service install/remove/status commands. These new guards validate the managed directory against process.getuid() before selecting/dropping to the service owner. Installation and removal explicitly require UID 0 in viewer-service-runtime.ts:71, whereas the existing service contract requires the library to belong to the selected non-root account at :198. The new check makes those requirements incompatible.

Observed evidence: service-repro.cjs enrolls an isolated normal-user library and simulates only process.getuid() returning 0. Production install, uninstall, status and queryViewerServiceProcess all reject with 'Managed directory must be canonical and owned by the current account'. No manager command executes. This is a deterministic UID simulation backed by the actual code path, not a real privileged install or setuid experiment.

Impact: an existing service can continue running under its normal user, but enrolling the library prevents supported administrative installation, removal and administrator status inspection. The guard in queryViewerServiceProcess prevents its existing builtins-only privilege-drop helper from ever reaching the selected-user status check. This violates the explicit preservation of viewer/control/service lifecycles.

Correction: perform managed identity validation under the verified selected service owner's identity before manager operations, using the existing privilege-drop seam. Keep canonical-home, clone, ownership and reader-identity checks. Do not weaken them by permitting arbitrary root access to user-managed stores. Address raw-home/named selection as well as the direct service helpers. Add managed service tests with distinct administrator and owner identities and a recording manager, including removal and status of an already installed definition.

4. High: a receiver permanently abandons independent pull after a temporary upstream history gap.

Primary location: packages/cli/src/sync-client.ts:157-159. Related code: sync-http-server.ts:245 and :515-516; sync-reconciliation.ts:413-422; sync-store.ts:846-856; sync-worker.ts:261.

Trigger: A->B->C routes are correctly configured, but C's worker starts pulling from B before B has acquired complete trusted history for A. B correctly returns HTTP 409 with trusted-history-unavailable. checkResponse discards that error code and substitutes remote-rejected. The reconciler treats 409 as permanent, so the worker persists blocked=true instead of using the explicit periodic history-wait path in recordRouteRun.

Observed evidence: history-repro.cjs runs the production C worker in-process and the production B HTTPS ingestion listener. Its initial pull produces attempts=1, lastError='remote-rejected', blocked=true. A then pushes actual history and body to B using the real reconciler; B's authorized inventory contains the live record. Over another 2.5 seconds with C configured to reconcile every second, C makes zero additional requests, retains the identical blocked retry and has zero documents. Calling the explicit retry operation makes that same worker fetch the document successfully. No mapping, trust or credentials change.

Impact: startup ordering or a recoverable upstream history interruption permanently disables the independent pull path until operator intervention. A working push may conceal it, leaving no independent repair when push is unavailable. Refusing live data before trusted history is correct; permanently suppressing checks after the history becomes available is the defect.

Correction: decode a strictly bounded, validated protocol error envelope and preserve the finite set of recognized error codes, or use an explicit retryable HTTP status for this condition. Keep history unavailable distinct from invalid history/signature/scope. The existing history-only delayed retry must work identically for local and remote history gaps. Add a real receiver-worker test that waits for upstream history, then catches up without explicit retry. Current history-only relay tests exercise the local-error path.

5. Medium, maintainability assessment: the storage module and lifecycle integration need a narrower interface and clearer actor ownership.

Locations: packages/cli/src/sync-store.ts:52, :526, :833, :1002, :1348, and packages/cli/src/sync-lifecycle.ts:7 plus the service call sites above.

The new storage file is 1,877 lines with more than 40 public async operations. It combines durable mutation/recovery and shared apply with reader projections, migration, identity maintenance, scheduling/backoff, worker configuration, and process-local communication cancellation. The single mutation authority is justified: body installation, terminal state, contributions, outbox and receipts must commit under one lock. It does not require all scheduling policy and deterministic ledger decisions to live in the same class, or every caller to understand the entire mutable ledger.

The scattered lifecycle preflights are also a concrete structural regression, not just repeated text. Each generic guard assumes the current process is the storage owner; adding it at privileged service seams caused finding 3. Retry meaning is spread across server HTTP status, client code translation, reconciliation classification, store string comparisons and scheduler filtering, which caused finding 4.

Request targeted decomposition before acceptance. Keep one private recovery/mutation/commit runner and the shared apply path. Put deterministic route/history/receipt/outbox transitions behind private typed functions over an already validated ledger; retain persistence in the one authority. Put retry classification in one finite typed result contract used across transport, reconciliation and durable scheduling. For legacy viewer integration, retain guards at public effectful seams but distinguish selected-owner validation from administrative orchestration; do not repeatedly run owner-only checks through nested internal calls. Use ordinary functions and existing privilege-drop helpers, not new backend classes or a speculative storage framework. File splitting alone would not address the problem.
