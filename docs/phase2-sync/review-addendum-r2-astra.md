N1. HIGH, proven event-order/lifecycle defect: an outgoing body response can retain a busy session and route attempt forever after its socket closes.

Primary location: packages/cli/src/sync-http-server.ts:449. The preceding asynchronous pin is at line 441; busy state starts at line 439 and is cleared only by the finally at line 451. Expiry explicitly excludes busy sessions at line 83. Route quiescence waits for attempts in packages/cli/src/sync-store.ts:597.

Trigger: an authenticated pull has established its session/history. Its GET starts pinOutgoing, then the client times out, cancels, disconnects, or the server's socket deadline expires while that asynchronous operation is still waiting. When pinOutgoing eventually resolves, the response is already closed. The new Promise registers response.once("close") only then, after the sole close event has fired. response.end on that destroyed response does not emit another close. The await never settles, so neither session.busy nor the enclosing registered attempt/activeRequests counter is released.

Evidence: busy-lease.cjs uses two real ManagedSyncStore instances, the production reconciler/client and HTTPS ingestion handler. A bounded gate at the source's pinOutgoing seam delays the real outgoing operation until the real client's 250 ms request deadline closes the response. The source lease is shortened to 1,600 ms. After releasing the gate and waiting another 1,900 ms, both runtime runs show sockets=0, sessions=1, cachedBytes=590, activeRequests=1, response.closed=true, and one late close listener. Direct route quiescence times out. The timing delay is deliberately injected at the production operation seam; it is not a measurement of a naturally slow physical disk. The lost event and retained production state are observed, not inferred.

Impact: this leaks a session, cached cut, request count and cancellation registration after an ordinary interrupted pull. Repeated occurrences can consume the eight-session admission limit; that exhaustion is inferred from the reproduced permanent leak and the configured bound, rather than an eight-leak load run. Route removal cannot establish quiescence for the leaked attempt. Waiting for the lease does not recover it.

Minimal safer correction: observe response close/completion before the first asynchronous pin operation, and explicitly handle an already destroyed/closed response before writing or waiting. Couple request termination to attempt cleanup. Ensure every exit releases busy state and the attempt exactly once; do not fix this by purging genuinely active transfers. A small direct response-lifecycle helper is sufficient; no new storage or scheduler abstraction is needed. Add an actual interrupted-pull test that delays pinning beyond cancellation, then asserts zero requests/sessions after cleanup, successful quiescence and continued admission without restart.

N2. HIGH, proven recovery defect: a truncated protocol error permanently blocks autonomous pull.

Primary location: packages/cli/src/sync-client.ts:180-182, within checkResponse starting at line 158. The catch covers both asynchronous response consumption and envelope validation. Related paths: request's response-truncated mapping at line 128; packages/cli/src/sync-failure.ts:39; packages/cli/src/sync-worker.ts:259 and :287.

Trigger: a correctly authenticated server sends a recognized non-200 error, then transport closes before its small JSON body finishes. The response iterator throws a transport error. The broad catch changes it to SyncProtocolError(409, "invalid-response-envelope"). The request wrapper then preserves that SyncProtocolError rather than classifying the incomplete response as transient. The worker persists blocked=true and stops checking the route.

Evidence: truncated-error.cjs creates A, B and C as actual managed stores, uses B's production HTTPS ingestion server and the actual owned C worker, and starts C's delegated-origin pull before B has A's trusted history. A synthetic verified-TLS loopback proxy forwards the genuine upstream 409 trusted-history-unavailable response, writes only its first eight bytes, then closes that response exactly once. C persists attempts=1, lastError=invalid-response-envelope, blocked=true. A subsequently pushes its genuine history and body to B through the production reconciler. Over 2.6 seconds with C's one-second reconciliation interval, C's request count stays 1 and C has zero documents. Explicit retry on the unchanged route then imports the document. This exact result was observed on both runtimes.

Impact: one recoverable transport interruption can indefinitely disable independent pull until operator retry. The same broad catch also handles incomplete other non-200 responses; the demonstrated case is the actual remote-history 409, not a separately reproduced 503 case. No trust, target or credentials were changed to recover.

Minimal safer correction: distinguish response-stream failure from completed invalid envelopes. Let incomplete response/transport failures retain the existing bounded transient retry classification, and retain local cancellation semantics. Validate status/code/exact fields only after complete bounded consumption. Keep completed malformed, unknown, oversized and unauthorized responses blocked; do not trust an incomplete error code as a history hint. Add the actual worker/proxy regression and require automatic catch-up without explicit retry after the one dropped response.
