Proven root cause: pass-wide outgoing credential resolution in startOwnedSyncWorker/drain snapshots old file contents before per-route eligibility is checked. While that pass works on the unrelated first route, token replacement and explicit store.retry can make the rotated route eligible. The pass then uses its previously captured old token for a new revision-2 identity request. Receiver uses the correct next token, rejects with 403 unauthorized, and source recordRouteRun persists blocked=true again. Subsequent passes read fresh files but isRouteDue skips the now blocked route. Explicit retry was consumed by stale pass credentials. This is an admission failure before trusted terminal history/current-revision custody, not a missed ping or a longer receipt-persistence wait.

Ranked falsifiable hypotheses published before instrumentation:
1. Stale work crossing explicit retry writes a new unauthorized block. Supported and refined to stale pass credential snapshot, rather than a request already active at retry.
2. Token rewrite produces credential-unavailable. Refuted in traced failure: resolver unavailableRouteIds empty; real identity request uses old snapshot despite both token files already matching.
3. Receiver stale credential resolver rejects a fresh token. Refuted in traced failure: receiver resolver matches current and next files; sender resolver matches neither. Receiver authentication is behaving correctly.
