## Ownership format and recovery boundary

New managed lock files use exactly `{schemaVersion:2,token,pid,start}`. New code accepts valid single-link legacy owner records. Older binaries reject the new format safely, so upgrade participating managed workers and CLIs together. This is not mixed-version managed liveness compatibility. Ledger, runtime-record and replication wire schemas do not change.

The candidate is written, synced, closed and reopened before publication. After linking, and again after removing the candidate, the retained file handle is synced before the checked parent directory. Recovery uses the same order. No protected operation starts before the required flushes and validation complete. Errors, including an operation that completed before reporting failure, preserve uncertainty and allow cleanup only of proven-owned names. A release failure does not imply rollback of an already committed report.

A coordinator compound-error probe exposed one remaining reporting defect: a candidate-write EIO followed by a first-close rejection returns only the close error. Acquisition correctly fails, the second close occurs and no owned names remain, but the original cause is lost. This is not evidence of unauthorized acquisition, foreign unlink or data loss. The original isolated ownership writer is correcting it under a [separate error-preservation gate](qa-lock-error-contract.md), with unchanged ownership, flush and platform rules. The red receipt and any nested-path corrections remain subject to both runtimes and the combined checks.

Existing empty, partial, unknown or unsafe canonical locks are not automatically removed. Interrupted `.reap` guards and ambiguous process identity can still block recovery. macOS live PID reuse remains conservative because its stored start identity is null. Pre-install candidate leftovers are non-authoritative; repeated crashes can accumulate them because general scavenging is deferred.
