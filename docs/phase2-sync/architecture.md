## Storage and mutation

Use a per-inbox versioned managed store with an authoritative bounded JSON ledger and external immutable bodies. Node 20 remains the package runtime floor; do not add a dependency on experimental `node:sqlite`. The ledger holds canonical origin states, original metadata, body descriptors, destination memberships, mapping contributions, suppression, tombstones, route revisions, outbox obligations, repeatable receipts, full inventory checkpoints and persistent worker/retry status. HTML bodies never enter the JSON ledger.

Serialize mutations with one cross-process inbox lock, including publish, deletion, enrollment, import commit, mapping revision changes and retry/receipt updates. Lock acquisition has a deadline. Ownership must distinguish a dead owner from PID reuse or a live process; unknown ownership blocks instead of stealing. Readers use atomic snapshots and immutable files and do not need a writer lock for the full read lifetime.

Lock files use exclusive creation, random ownership token, PID and process-start identity where the platform supplies it. Reclamation requires conclusive owner death and ownership recheck; PID age or wall-clock lease expiry alone is insufficient. Use same-process serialization as well, since concurrent promises otherwise share a PID. Default acquisition deadline is 10 seconds. Cap a ledger at 10,000 canonical records and 64 MiB serialized metadata; reaching capacity blocks new records rather than dropping old tombstones. A deletion updates its existing record and must remain possible at capacity.

For body installation, take ownership of the caller's bytes before the first asynchronous operation. Hash the owned creation buffer once. Incoming transfers count/hash actual chunks in private bounded staging and perform existing UTF-8 and HTML validation. Fsync the completed body and containing directory before committing its reference. Ledger replacement writes a unique private file, fsyncs it, atomically renames it, then fsyncs its directory. No durable receipt is sent before this sequence completes. A failed fsync is a failure, never a success. Target platform/filesystem support is explicit; unsupported durability blocks enrollment rather than silently skipping flushes.

All newly created store/parent directory entries are flushed. Body sequence is exclusive private stage creation, bounded write/hash, file fsync, immutable final rename, final-directory fsync, then ledger commit. The supported durability claim is process crash plus host restart on local POSIX filesystems honoring file and directory fsync and atomic rename. It does not cover dishonest storage hardware, arbitrary backup rollback or filesystem corruption. Platforms without the required primitives fail explicitly. A rename followed by failed directory fsync is an uncertain outcome: return error and block additional mutations in that process. Recovery reads and validates the visible snapshot, fsyncs the snapshot and directories to establish a durable baseline, then resumes. Do not delete a final body merely because the call returned an uncertain result.

Publication commits descriptor and route obligations in the same ledger snapshot. A committed record is the recoverable obligation source, so bootstrapping a mapping and concurrent publication cannot miss a record. Owner deletion commits a terminal signed state and supersedes pending live work in one snapshot before body cleanup. Receiver installation commits applied state, destination membership, route contribution, receipt and onward obligations together. Unreferenced staging/body files are harmless crash leftovers; cleanup must never remove referenced bodies or terminal states. Tombstones are retained indefinitely independently of receipt/outbox cleanup.

Initial implementation may defer general orphan garbage collection. Any body cleanup shares the mutation lock with final installation. An outgoing transfer takes an owned bounded byte buffer or opens its immutable file under that lock before release; that buffer/open handle pins its bytes until completion. Persistent pending obligations retain their live body references. Superseding an add with a tombstone must not invalidate an already opened handle, and deletion cleanup can retry after handles close. Lockless reader disappearance returns unavailable and never invents a tombstone. Physical reclaim status must be honest if cleanup is deferred.

Enrollment uses an explicit recoverable migration intent. Move legacy documents to the new managed storage area and replace the old `documents` path with a regular format barrier. Older mutating CLIs then fail their directory check before changing originals. Upgraded backend and read-only source choose the new store. Migration recovery recognizes every intermediate phase and completes or blocks without guessing deletion. This is a storage format upgrade; old readers fail safely and upgraded viewer/control/service behavior remains intact. Do not rely on a marker old binaries never check.

Exact order: persist and flush migration intent, evacuate `documents`, install the regular-file barrier with exclusive creation, flush affected directories, then enumerate/enroll the evacuated tree. Never enumerate first or activate while the old path is writable. If a legacy process recreates a directory at the old path during the transition, block recovery rather than merge it. A legacy process already past preparation must either have completed its rename before evacuation, so it is included, or fail its later path operation against the barrier. Recovery tests cover every intermediate state and repeated invocation.

Enumerate the actual legacy directory under the mutation lock. Validate every candidate rather than using reader listings that omit corruption. Enroll bounded batches with persisted progress; unknown records block complete inventories. Preserve case-sensitive legacy document IDs and metadata. Each body is hashed once during enrollment. Existing metadata parser extras must have an explicit validated representation, never be silently dropped. Once enrolled, managed bodies and origin metadata are immutable. External same-account modification is outside the writer contract and produces conflict/quarantine on audit or detected drift, never a changed digest under the same origin ID.

## Identities and trust

An inbox UUID identifies a logical library. Canonical record identity is origin inbox UUID plus case-preserved origin document ID. Signed state binds origin history epoch, monotone state version, live/deleted status, SHA256, exact byte length and a fixed validated original metadata projection. Local route/storage handles may differ from original document IDs. Visible uniqueness is destination UUID plus canonical identity. Different IDs with identical content remain separate. Several route contributions materialize one row.

The persisted format is `schemaVersion: 1` in `<home>/sync/ledger.json`. Top-level fields are `inboxId`, `historyEpoch`, `storageIncarnation`, `ownerAnchor`, `generation`, `nextOriginVersion`, `originKeys`, `records`, `routes`, `outbox`, `receipts`, `checkpoints`, `migration` and `worker`. Keys are serialized UUIDs and case-preserved safe IDs, using a collision-free canonical pair encoding. Unknown schema versions fail closed. Private key material stays private in the managed store and is never part of exported records.

Each record stores `originInboxId`, `originDocumentId`, `historyEpoch`, `version`, `state`, `metadata`, `sha256`, `byteLength`, `metadataSha256`, `signature`, `localId`, `bodyFile`, `contributions`, `suppressed` and `provenance`. A tombstone keeps the original immutable descriptor and has a larger origin version. `metadata` is the schema-1 original projection in the fixed order schemaVersion/id/title/type/createdAt/sourceFileName. `contributions` records mapping ID/revision plus attached/detached state. `localId` is only a local reader handle and must not replace the canonical origin document ID in wire metadata.

Each route stores its stable ID and monotone revision, local direction, expected immediate peer ID, peer HTTPS URL, source/destination inbox UUIDs, local named inbox binding, allowed origin UUID/epoch/public-key tuples, explicit delegation for complete origin history and redistribution, credential reference, TLS trust reference, active/reconnecting/detached/blocked state and last error. `outbox` entries bind route revision plus canonical key and origin state fingerprint, attempt count, next attempt time and persistent error/disposition. Receipt keys bind the same identity plus receiver storage incarnation. Checkpoints bind only complete scoped inventory generations. Contributions, receipts and checkpoints are separate structures.

Use per-origin Ed25519 signatures, with origin public keys pinned explicitly in each route's allowed origins. Relays preserve signed state and cannot mint owner tombstones. A route pins immediate source/destination peer identities, source/destination inbox UUIDs, route ID, revision, allowed origin keys and redistribution scope. Local paths are chosen only by trusted local configuration, never inbound requests. Configuring a route shows the selected existing named destination and reader audience. No global hash existence endpoint is exposed.

Complete history attestation is an explicit immediate-peer delegation for specified origins, separate from signature verification and permission to forward content. A relay without that delegation cannot unblock tombstone-first reconnection merely by presenting a smaller list. Signed origin states prevent it from fabricating owner events; the explicit delegation determines whether its complete scoped inventory may establish the history cut. Incomplete/error pages never establish that cut.

Canonical signatures use an explicit domain tag and fixed JSON array encoding of origin UUID/document ID, epoch/version, state, fixed metadata projection, SHA256, length and metadata digest. Manifest completion evidence binds protocol/domain, authenticated peer, route/revision, origin scope/epochs, generation, count, ordered descriptor digest and a fresh requester nonce. A live origin or explicitly delegated relay attests its current complete committed cut, never an arbitrary replayed snapshot. Relay completeness is valid only for enrolled origins with retained verified terminal history and no known restore/inventory gap. It is a scoped delegation of the relay's current durable origin-state view, not a claim that an unreachable origin has made no later changes. Without trustworthy complete history, accept valid terminal states but block live reconnection/forwarding.

Each store records a storage incarnation and an ownership anchor for its canonical home/filesystem identity. A copied or moved store requires an explicit clone/fork or restore procedure. Clone creates a new local inbox/origin identity for future originals and cannot silently keep owner credentials. Restore rotates storage incarnation, invalidates historical receipts/checkpoints and requires full trusted terminal-history reconciliation before live state is reattached or forwarded. Peers pin epochs and reject inconsistent owner histories. A byte-for-byte clone with all credentials and an identical undetectable environment cannot be automatically distinguished; document that limit and block detected mismatches.

Receiver storage restore and origin-owner recovery are separate. Receiver restore changes custody incarnation and forces holdings/manifest reconciliation. An origin restore cannot resume signing merely by changing epoch: the former owner must be fenced and complete terminal history recovered under an explicit trusted transition. Known terminal states survive that transition. Until then owner mutation, copied credentials and communication grants remain blocked. Safe fallback is a fresh fork for future originals with inherited records detached; no silent identity union or resurrection. An implementation may provide safe quarantine and an explicit fork while leaving trusted owner-recovery tooling unavailable; that limit must be reported and tested.

## Transport and inventory

Protocol version 1 uses HTTPS only for both Tailscale and LAN. Use normal hostname/certificate verification with an explicit private CA option. Never set certificate bypass options or follow arbitrary redirects. A route-scoped high-entropy credential authenticates each immediate peer operation in addition to pinned identities. Use timing-safe token comparison and redact secrets. Reader and local admin/control listeners do not ingest replication data. The dedicated ingestion listener has explicit TLS configuration and no process-control operations.

Use bounded descriptor offers, verified body transfer, current holdings, complete inventory and durable receipts. Both push and pull call the same validation and apply/commit functions. Offer/body-exists/202 never count as custody. A receipt binds storage incarnation, receiver UUID, destination UUID, mapping ID/revision, canonical identity, signed state and descriptor. Historical receipt lookup is separate from current body availability, checked with file presence/regularity/length without routine body reads.

Wire paths are fixed under `/sync/v1`: identity, manifest, holdings, offer and body. Every operation except a non-disclosing health response requires the same route ID/revision and scoped authorization. Requests cannot supply a filesystem path. Maximum HTML size is the existing 10 MiB default; maximum descriptor is 64 KiB; manifest pages contain at most 128 descriptors with a 60-second generation lease and bounded total entries. Reject oversize headers/bodies and compressed transfer encodings. Server request, header, idle and whole-attempt deadlines are finite. Incompatible protocol versions block rather than downgrade.

Complete manifests have a generation bound to one immutable ledger cut, exact scope, bounded page size and opaque pagination. Retain the cut for a finite lease, or reject changed-generation pagination and restart. Mark completion only after every page validates. Per-item receipts never advance a complete-inventory checkpoint. Missing or corrupt inventory is an error, never deletion. Inbound body and descriptor limits are independent; no compression is initially supported.

Receiver commit revalidates current route revision, target inbox identity, trusted origin state and terminal tombstones under the same mutation lock. A locally revoked grant fences a late upload. A sender's local cancellation cannot undo a completed remote commit. Revocation cancels local active work and retires every operation under the old revision, including probes, pull, retries and deletion-only requests.

Explicit reconnection always uses a fresh revision. It remains blocked until peer identity and scope are revalidated and a complete trusted terminal-state inventory is applied. Reconcile tombstones before live reattachment and onward forwarding. Unavailable, missing or untrusted history leaves retained data detached. Other authorized routes operate independently; verified terminal origin state dominates all managed contributions.

## Worker and foreground delivery

One explicitly enabled worker per inbox handles its routes and separate ingestion endpoint. It outlives publish and viewer processes, uses its own ownership record/lock and has explicit enable/start/status/stop/disable commands. Foreground mode supports process supervisors; background mode uses a detached child and authenticated ownership checks. No system service is installed automatically. Document boot supervision commands; enabled workers restart on sync/publish entry and an explicit startup invocation. Startup, timer drift after suspend, network recovery and explicit wake trigger a full catch-up pass. Receiver independently pulls periodically even when push succeeds.

Status distinguishes enabled, running and boot-supervised. Boot supervision is an observable prerequisite, not implied by an enable flag or the next CLI invocation. Supply a foreground worker command and local systemd/launchd supervisor templates without installing them. Report setup-required until a supervisor is explicitly configured; no production service installation is authorized here. Verify process restart with disposable supervisor/worker subprocesses and verify viewer shutdown leaves sync running.

Every catch-up queries current receiver holdings for active outbound routes even when the outbox is empty. Missing acknowledged bodies durably recreate repair obligations. Catch-up also reconciles approved inbound inventories. A complete run treats tombstones first. Relay scheduling is derived from canonical current state plus authorized route receipts, never from a new local event on every receipt. Cycles terminate through canonical uniqueness and per-route applied-state receipts.

Defaults: 30 seconds overall foreground wait, 5 seconds per network attempt, one transfer at a time per worker, periodic reconciliation every 30 seconds, exponential retry from 1 second to 5 minutes with jitter, and a finite maximum consecutive transient-attempt count before persistent blocked state. Settings validate finite positive bounds. Explicit retry resumes blocked work; no obligation disappears at a retry limit. Authentication, identity, schema, quota, integrity and revoked-scope errors block without a busy loop. Stored status shows target, pending/confirmed/blocked/detached, attempt count, next attempt and last error. Deletion is pending until each active authorized hop acknowledges its own terminal state.

Normal publish waits only for the intended server's recoverable durable receipt within the configured deadline. Output distinguishes local durability from confirmed delivery and from onward completion. Timeout/SIGINT abort foreground waiting/current request where possible, leave saved content and queued obligations, and report pending. Explicit retry pause is separate. Persistence failure is an error. Uncertain commits resolve through idempotent holdings/offer reconciliation.

Existing public/static/cloud export workflows must not acquire permission to export managed imports from ordinary list membership. Export originals by default or reject expansion without an explicit policy; sync does not create that policy. Ordinary reader list/search/view includes imports, with escaped origin and detached badges. Existing original-byte rendering, sandbox and CSP remain unchanged.
