# Managed storage implementation

This guide describes managed storage and local reader/backend integration. Delivery and scheduling are documented in `protocol-interface.md` and `worker-interface.md`; current verification and limits are in `acceptance.md`.

## Entry points

`ManagedSyncStore` in `packages/cli/src/sync-store.ts` owns one explicitly selected existing inbox home. Construct it with a canonical absolute path. `enroll()` is the opt-in format upgrade. An unenrolled `LocalDocumentBackend` retains its legacy behavior and does not request file or directory fsync support.

Enrollment persists migration intent before evacuating `documents` to `sync/legacy-documents`. It creates a regular-file format barrier at the former path before enumerating actual candidates. A legacy writer already prepared against the old path cannot finish its later rename against that barrier. Unknown candidates and unsupported metadata fields block completion. Batches of 32 records persist progress. Legacy IDs retain case, metadata retains its original field values, and identical bodies under different IDs remain distinct records. Legacy metadata without a schema field receives the existing schema-1 interpretation. The general legacy metadata parser still ignores unknown extras; enrollment explicitly rejects them instead of silently signing a lossy projection.

`LocalDocumentBackend` selects this store after enrollment. `LocalDocumentSource` uses only atomic snapshots and read-only file handles, preserves its selected HTML byte limit, and never prepares storage, chmods, fsyncs, locks, or migrates. Ordinary list/search/view includes imports with validated origin metadata and detached badges. Static export, including the existing cloud snapshot path, filters imports before fetching bodies and rechecks origin on each fetched document. Fork-inherited originals are imports for this purpose.

## Protocol callers

Both future push and pull receivers must use `apply(authorization, descriptor, optionalBuffer)` or `applyStream(authorization, descriptor, asyncChunks)`. These validate descriptor bounds, pinned Ed25519 origin state, exact immutable metadata, byte length, digest, HTML and UTF-8. Buffer ownership is taken before the first await. Streaming chunks are copied before each asynchronous write. Staging happens before the final lock so local revocation can fence a transfer at commit. One locked ledger replacement commits canonical state, contribution, receipt and all currently authorized onward obligations. Live onward work lacking complete terminal history persists blocked until that history is established.

The store authorization object binds `routeId`, `revision`, `peerId`, `sourceInboxId`, and `destinationInboxId`. These are trusted local authentication results, not substitutes for HTTPS peer and credential verification. Future transport handlers must authenticate the immediate peer and resolve the local route before passing them. No operation accepts an inbound filesystem path. `configureRoute` validates HTTPS origins, explicit allowed origin UUID/epoch/public-key tuples, redistribution and complete-history delegation, local named inbox and reader audience, and opaque credential/TLS references. This phase does not provision or read route credentials or CA files.

`apply` without bytes returns `needs-body` when current custody is unavailable. Other results carry the exact durable receipt. Suppressed and superseded results do not claim live body custody. Terminal origin state dominates later stale live offers regardless of their version. Conflicting immutable metadata, digest, epoch or same-version states fail instead of overwriting records.

`holdings` reports current stat-based body availability separately from historical receipts. Its availability check does not open HTML. `inventory` returns one generation and all scoped descriptors from an atomic ledger snapshot. Future transport code must paginate that immutable cut or reject changed generations, enforce the 128-entry page and 60-second lease limits, authenticate completion evidence, and supply a fresh requester nonce. Protocol holdings and inventory calls automatically establish a recovery baseline after a process restart; callers may also invoke `recover()` explicitly. Recovery flushes the validated visible ledger and directories, without opening HTML bodies.

`completeInventory` accepts only a complete descriptor set whose scope, generation, count, digest and nonce match the authenticated completion evidence. It checks explicit relay completeness delegation separately from origin signatures. It applies tombstones before reattaching live contributions or enabling onward delivery. Per-item receipts never advance this checkpoint. Fresh outbound revisions can expose complete terminal-history descriptors while reconnecting; body pinning remains blocked until activation. A relay with detached or unknown source history cannot claim completeness.

`acknowledge` persists a validated per-route receipt before retiring the matching sender obligation. `reconcileHoldings` recreates repair obligations even after confirmation and pins the receiver storage incarnation observed by that repair. An old receipt from a replaced incarnation cannot retire it. `updateAttempt`, `retry`, and `setWorkerState` persist later worker bookkeeping without running a worker. Route revocation advances its revision, detaches contributions, and retires old obligations. No deletion-only grant survives.

`deleteDocument(localId, capturedIdentity?)` preserves its existing one-argument behavior. The optional validated identity binds a viewer or hub writer to its canonical home, device/inode and inbox UUID. Checks run before namespace mutation or writable recovery and again under the managed ownership lock. A replacement or mismatched identity raises `ManagedDeletionIdentityError` before ledger changes. The public deletion factory maps that specific conflict to its existing identity error; genuine storage, signature and cleanup errors retain their failure meaning.

The same factory serves legacy and managed layouts. Completed enrollment on the same captured root and UUID switches a capable live writer to managed deletion. Invalid or incomplete managed state cannot reactivate the legacy purge worker. Originals create signed tombstones; imports are suppressed locally. This adds no ledger, runtime, wire or ownership-record schema.

`pinOutgoing` returns an owned bounded byte buffer read under the mutation lock. Readers and outgoing transfers do not depend on later file lifetime. General orphan/body reclamation is deferred, all referenced bodies remain retained, and deletion reports zero reclaimed bytes honestly. Tombstones remain in the ledger independently of receipt/outbox state. The ledger rejects new canonical records at 10,000 and all snapshots above 64 MiB; HTML is limited to 10 MiB and descriptors to 64 KiB. Capacity errors never drop terminal records. Commits reserve space inside the 64 MiB limit for live-state version growth and possible inbound terminal receipts, so filling metadata cannot block the owner deletion update.

## Durability and recovery limits

Managed enrollment requires a local POSIX filesystem honoring regular-file fsync, directory fsync and atomic same-filesystem rename. This implementation exercises those calls successfully on Linux x64, Node v24.19.0, using disposable tmpfs stores in /tmp. Those tests establish process-crash and syscall behavior, not physical persistence across a host restart; production requires persistent storage honoring the stated fsync contract. Flushing an existing canonical parent does not require ownership; creating or reading managed store directories and files still requires the current account. Precreated mutable managed directories are hardened to mode 0700. Owner key files require mode 0600 or stricter private permissions. Read-only consumers never harden paths.

The sequence is private exclusive stage, write, file fsync, immutable destination rename under the lock, body/staging directory fsync, exclusive ledger temporary file, ledger file fsync, rename, and ledger directory fsync. Failed file or directory flushes are errors. An uncertain outcome after rename blocks further mutations for that inbox throughout the current process until explicit recovery. Recovery validates the visible snapshot and flushes the snapshot and directories to establish a new baseline. It does not infer rollback, remove final bodies, rehash routine scans, or invent deletion from missing files. Explicit `audit()` detects changed body bytes and quarantines without changing the expected descriptor. Missing bodies remain repairable live records.

Lock acquisition is bounded to 10 seconds by default and serializes promises in the same process and writers in different processes. Exclusive ownership records contain a random token, PID, and Linux boot/start identity when available. Only conclusive owner death permits reclamation after an ownership recheck. Unknown/live ownership blocks. A separate exclusive reaper guard serializes reclamation; an interrupted reaper may require explicit local inspection. No wall-clock expiry steals a lock. Other POSIX platforms without process-start identity use conservative live/unknown PID handling.

Managed atomic publication uses the versioned completed-candidate protocol in qa-lock-creation-contract.md. Its result retains `owner` and `release()` and adds `closeHandles()`, which disposes descriptors while retaining namespace evidence. Both managed and portable results coordinate release and disposal. Reaper snapshots distinguish unverifiable records from actual filesystem or cleanup failures. An operational or compound failure rejects that acquisition before protected work; malformed, unknown and unsafe evidence still never establishes owner death. General private-file and HTML hardlink checks are unchanged. The exact corrective rules are in qa-shutdown-ownership-contract.md.

Portable validation snapshots retain both validation and disposal causes and use the same bounded close retry as managed snapshots. The ownership reader also disposes its temporary snapshot through that helper. It still returns unknown on a close failure even if retry closes the descriptor; cleanup cannot grant ownership. Permanent OS close rejection remains uncertainty, with no promised physical descriptor closure. These lock-only corrections add no directory-fsync demand to portable catalog operations.

The durability claim excludes dishonest storage hardware, filesystem corruption and arbitrary backup rollback. A byte-for-byte clone with credentials and an indistinguishable environment cannot be detected automatically. Detected home/device/inode anchor mismatches block ordinary reads and mutations.

`quarantineRestore()` is explicit. It rotates the storage incarnation, clears receipts/checkpoints, blocks all routes under fresh revisions, disables the worker and owner signing, and removes copied owner private keys. It does not reattach live imports. `fork()` is the available safe continuation: it creates a fresh inbox UUID, epoch and signing key for future originals, retains inherited records with their former canonical identity as detached imports, and clears copied communication grants. A persisted `forking` migration state recovers interrupted reader-identity replacement. Unexplained `instance-id` changes fail closed. Trusted owner-history recovery and reattachment without a fresh fork are intentionally unavailable in this phase.

## Fault hooks and counters

Hooks are constructor-injected only through `ManagedStoreOptions.testHooks`. Production reads no fault environment variables. `createOneShotStorageFault(event, optionalAction)` arms exactly once and exposes `{ event, armed, hits }`; proof contains no paths, keys or credentials. A subprocess test can supply an action that signals IPC and stops or exits the synthetic child.

Events include migration intent/evacuation/barrier/enumeration, body staged/flushed/installed/directory-flushed, ledger temporary written/fsynced/renamed/directory-fsynced, committed-before-receipt, and receipt-before-retirement. File flush event hooks occur after actual fsync; syscall failure tests can inject failures into `FileHandle.sync` separately. `counters.events` counts each reached barrier. `htmlOpens` counts successful body read opens, `htmlBytes` counts actual read bytes including partial reads, `hashPasses` counts body hash attempts, and `bodyTransfers` counts incoming attempts that write bytes, including failed verification. Metadata hashing and ledger/metadata reads are excluded from body counters. Five unchanged scans, including receipt/apply and holdings queries after recovery, require zero HTML opens/bytes, body hash passes and body transfers.

The sibling fault and HTTPS fixture suites are owned and integrated by the parent. Their results are not claimed as results of this storage writer's commands. Real two-host LAN, Tailscale and sleep/wake behavior remains untested.

Portable acquisition disposes the entire newly opened descriptor lifetime on failure, including a failed initial stat. Existing bounded close/error-preservation helpers retain acquisition, inspection/unlink and cleanup causes. Without initial inode evidence, the unknown name stays intact while its descriptor is disposed. Ordinary portable catalog use still has no managed directory-fsync or POSIX-enrollment requirement. A permanently rejecting OS close remains explicit uncertainty.

## Route attempt lifetime

`openRouteAttempt(authorization, parentSignal?, deadlineAt?, locallyInitiated?)` returns an attempt signal and `close(): Promise<void>`. First close immediately stops watcher admission and returns one cached promise that joins the complete admitted check, including lock acquisition and release. Client, reconciliation and ingestion owners await it before completing their own lifetimes. The parent abort listener and active-attempt registry entry remain until that join settles. Do not await close from the attempt's own check or while holding a lock the check needs.

Normal close cancels only the private authorization watcher. It preserves the public signal unless a real authorization or storage check aborts it. Watcher failures retain the existing generic public-abort classification; close does not expose raw storage errors or certify successful namespace release. It does not own detached body pins or prevent future route attempts. Callers requiring a route fence must persist that fence before quiescing existing attempts.

`withStoreLock(directory, deadlineMs, operation, signal?)` accepts an optional signal. The watcher uses it to cancel queued acquisition without bypassing another holder; cancellation after acquisition still awaits ownership release. Existing signalled ownership callers cancelled in the native retry timer receive their exact `signal.reason`, rather than Node's timer wrapper. Filesystem and compound cleanup errors remain separate. Unsignalled calls and ordinary portable catalog registration retain their behavior. Already-entered native I/O may outlast a caller's existing deadline.
