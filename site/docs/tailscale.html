Use HTTPS inside your tailnet

HTML Inbox integrates with an existing signed-in Tailscale client. Tailscale Serve terminates HTTPS and proxies the live viewer on loopback.

Prepare the existing client

Install Tailscale and sign in separately before running HTML Inbox. The client must be connected, MagicDNS and HTTPS must already be available, and the account running the viewer must have permission to use Serve. HTML Inbox checks these prerequisites without accepting setup or consent prompts.

Reader access follows your tailnet policy. HTML Inbox does not install Tailscale, log in, change ACLs, grant operator permissions, enable public Funnel, or reset Serve configuration.

See Tailscale's Serve guide and HTTPS setup guide if you need to configure those prerequisites yourself.

Start Tailscale mode

html-inbox viewer stop
html-inbox viewer --tailscale

The backend binds exactly 127.0.0.1. Serve owns the root route on HTTPS port 443 for the connected device's exact hostname. The command returns a verified URL such as https://server.example-tailnet.ts.net. It verifies the client state and proxy route rather than trusting a URL printed by the client.

--port selects the loopback backend port, not a different public HTTPS port. --host must remain 127.0.0.1 in this mode.

When the intended executable is not on PATH, set an explicit existing path. Successful startup saves its absolute path for detached restarts and boot configuration. 

HTML_INBOX_TAILSCALE_COMMAND=/absolute/path/to/tailscale \
  html-inbox viewer --tailscale --port 4321

Preserve existing services

HTML Inbox inspects the complete Serve and Funnel configuration before changing it. An occupied root route or conflicting port-443 listener is refused. Mounts that intercept the viewer's /assets, /documents, or /health routes also conflict, including relevant cleaned path and trailing-slash aliases.

Unrelated mounts, other ports, named services, and unrelated Funnel settings remain unchanged. A matching proxy target without HTML Inbox's private ownership journal is still someone else's route and will not be adopted.

The journal at tailscale-serve.json in the inbox records the connected node, hostname, exact route and backend, executable, and inbox/process identities. It records pending intent before startup and active ownership after verification. Keep this file private and preserve it during recovery.

Inspect and clean up

html-inbox viewer status
html-inbox viewer stop

Status reports drift or unavailability if client state or the live route no longer matches. It does not report a stale HTTPS URL as ready. Stop verifies ownership and removes only the recorded root route, then verifies that unrelated configuration survived.

The scoped removal uses tailscale serve --bg --yes --https=443 --set-path=/ off. HTML Inbox never uses a global Serve reset. If the route already disappeared, verified cleanup can clear its journal without a mutation. If ownership is uncertain, it retains the journal and reports the reason.

A failed startup uses the same scoped cleanup. Switching to loopback or LAN also requires retained Tailscale ownership to be resolved before a backend port is reused. Restore the existing client's connectivity or permissions, then retry viewer stop.

Recover configuration drift

Inspect the current Serve configuration and the error before changing anything. 

tailscale serve status --json
html-inbox viewer status

If another service added a mount that shadows a viewer route, move that conflicting mount yourself. HTML Inbox can still remove its exactly verified root route while preserving the external mount. A changed node, hostname, root target, or unsafe listener is not treated as owned cleanup.

If the recorded executable moved, set HTML_INBOX_TAILSCALE_COMMAND to the intended current executable for status and stop. An explicit override takes precedence during recovery; it does not bypass node or route ownership checks.

Recover a lock left by a forced kill

Mutations share one lock for the connected node across all inbox homes used by the same OS account. It lives under that account's native home at .html-inbox-tailscale/<node-hash>.lock. Changing HOME, TMPDIR, or HTML_INBOX_HOME does not select a different lock.

Graceful shutdown releases the lock. SIGKILL or a crashed command can leave it behind and retain a pending ownership journal. The error reports the exact lock path.

  1. Stop automation using this account and node. Verify that the viewer worker and its Tailscale command process group have exited. A saved PID alone does not establish process identity.
  2. Inspect owner.json in the reported lock directory. Remove only that verified stale node lock directory. Preserve the .html-inbox-tailscale parent and the inbox's tailscale-serve.json.
  3. Retry html-inbox viewer stop. It rechecks the exact owned route before removing it.

The CLI does not automatically reclaim a stale node lock or kill a PID from its record. If you cannot establish that the previous processes have exited, leave the lock in place. Do not use a global reset to get past it.

Account storage and compatibility

On POSIX, the account home must belong to the current UID and must not be writable by other users; the private lock directories use 0700 and the owner record uses 0600. On Windows, the lock uses the native account profile and inherited ACLs with symlink/junction and available identity checks. HTML Inbox does not audit NTFS ACLs. Follow Windows storage prerequisites.

Compatibility follows the reviewed current Serve command and JSON contracts, with no hardcoded Tailscale minimum version. Unsupported flags, unknown routing fields, malformed output, timeout, and permission failures produce errors rather than a fallback configuration. The source integration notes record the exact reviewed official source and CLI contracts.
