Resolve a failure without losing state

Start with the reported error and the selected inbox. Safety refusals preserve records and owned routes when the CLI cannot establish that a process or external configuration belongs to it.

Viewer does not start

Check the installed version, configuration, and private status first. 

html-inbox --version
html-inbox viewer status
html-inbox viewer --foreground

Foreground mode is useful after the existing viewer has stopped. A background startup failure reports viewer.log under the inbox. Inspect that private log for the original error rather than deleting records and starting again.

If the port belongs to another service or inbox, choose an unused port. HTML Inbox will not stop that service. If the current viewer is verified and you intend to change it, stop it first. 

html-inbox viewer --port 4321

Use the same HTML_INBOX_HOME across commands. An explicit HTML_INBOX_PORT must match the intended active port for status and stop; unset it when you want the saved configuration. Repeated starts reuse a healthy matching viewer, while explicit conflicting configuration is refused.

Older viewer record blocks an upgrade

Stop the old process with its previous executable before installing a newer release. For an old foreground process, use Ctrl-C. The new CLI refuses an older private control protocol rather than signaling an unverified PID.

If the older viewer already exited but left viewer.json, verify that its recorded process is gone and its listening port is unused. Then remove only that stale viewer.json from the selected inbox and retry. Preserve documents, saved configuration, and other journals. A PID record by itself is not proof of process identity.

A report is blank or missing assets

Read the publish warnings. Relative assets are not copied, external images and stylesheets are blocked, and only the documented Tailwind and Mermaid script entries are supported. Embed CSS, script, and data URLs into the HTML, then publish a new record.

Replace inline event attributes such as onclick with listeners in a script. Check that a CDN-dependent report has internet access. _blank and top-page navigation are blocked by the frame sandbox. See HTML compatibility.

A LAN device cannot connect

Confirm the active mode and current URLs with viewer status. Use the concrete IP, not 0.0.0.0 or ::, in a browser. Check the server's assigned address, client routing, and firewall TCP port rules. HTML Inbox does not configure firewall or router access.

If address discovery reports no usable interfaces, choose a valid explicit IP with --host. DNS aliases, unexpected Host values, forwarded-host headers, wrong ports, and scoped IPv6 authorities are refused. Use the emitted authority instead of putting a general reverse proxy in front of it.

Tailscale startup or stop fails

Confirm the existing client is installed, signed in, connected, permitted for Serve, and has MagicDNS and HTTPS already enabled. HTML Inbox will not run login, provisioning, or consent. Check tailscale serve status --json for conflicting root, port-443, or reserved reader mounts.

Restore the client or permissions and retry viewer stop when cleanup was retained. A moved executable can be selected explicitly with HTML_INBOX_TAILSCALE_COMMAND. Do not remove the journal or use a global reset to bypass ownership checks.

After a forced kill, an exact node-lock path may require deliberate manual recovery. Verify the worker and command processes exited, remove only that stale node lock, preserve the journal, and retry stop. See Tailscale crash-lock recovery.

A boot service is not healthy

Run viewer service status with the same custom home if one was installed. Inspect Linux journal output or the selected macOS inbox log. Ensure the installed Node, CLI, Tailscale, and certificate paths remain available to the normal account.

Stop an ordinary detached viewer before service installation. A login-only encrypted or unmounted home cannot provide before-login startup. Unrelated or edited definitions are refused; restore the exact owned definition or resolve the external service yourself. Failed manager operations report rollback failures rather than claiming success.

See boot diagnostics. Boot service installation is unsupported on Windows; ordinary viewer commands still work.

Remote publishing is incomplete

Check Wrangler authentication and the explicit account/project. Existing projects require deliberate adoption, and their production branch must match the configured branch. If a remote request may have succeeded, read status and reconcile instead of repeated publishing. 

html-inbox remote status
html-inbox remote reconcile

An abandoned mutation lock needs --recover-lock only after the previous command and children exited. Malformed locks, live or reused PIDs, shared-machine uncertainty, and recovery guards need the manual recovery procedure. Keep operation journals and snapshot work so reconciliation can use the original intent.

Storage is unsafe or inaccessible

Check ownership, regular-file/directory requirements, symlinks, and reported permissions. Do not make the whole inbox world-readable to get past a failure. On Windows, inspect root and child ACLs, especially after restoring or moving data.

An unsafe private log, hard-linked process record, symlinked managed path, or account-home node lock can prevent startup deliberately. Correct the specific path under the owning account and preserve documents and journals. See security and storage.

Report a reproducible problem

Include the CLI and Node versions, operating system, exact command with secrets removed, and the error. State the exposure mode and whether you use a custom inbox or boot service. Do not post capability URLs, private control URLs, API tokens, report contents, or complete private records.

Open a GitHub issue with a minimal safe HTML sample when rendering is involved. Redact diagnostics before sharing them.
