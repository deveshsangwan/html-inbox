Work on HTML Inbox

Use Node.js 24 for the source workspace and its release tooling. The published CLI continues to support Node.js 20 or newer.

Set up a source checkout

git clone https://github.com/deveshsangwan/html-inbox.git
cd html-inbox
corepack enable
corepack pnpm install --frozen-lockfile
corepack pnpm build
corepack pnpm html-inbox --help

The workspace pins pnpm in package.json and commits its lockfile. Use the pinned Corepack-managed version. The npm package is a self-contained executable with no runtime package dependencies; the source workspace has build and test dependencies.

Installed-user examples use html-inbox. From the checkout root, substitute corepack pnpm html-inbox for that command.

Run the verification gate

corepack pnpm exec playwright install chromium
corepack pnpm verify

The gate performs a clean build, unit and integration tests, Chromium browser tests, and an installed-package smoke test. For focused work, run corepack pnpm test for source tests or corepack pnpm build before testing compiled files.

Do not run compiled source tests concurrently with a clean build or package smoke in the same checkout, since those commands replace build output. Platform recording tests use temporary executables and paths. They are not proof of a real reboot, physical LAN reachability, or tailnet certificate issuance.

Read the architecture, threat model, and static remote inbox ADR before changing validation, storage, rendering, or reader exposure.

Keep changes reviewable

Use clear names and direct functions. Validate untrusted data at boundaries, then rely on the validated shape. Separate logical steps in function bodies and visually isolate guards. Prefer TypeScript inference for implementation details and useful explicit contracts at public boundaries.

Keep the viewer read-only, preserve metadata escaping and document isolation, and exercise process identity before adding any process action. Changes to external integration should use recording commands and temporary paths in tests, with real host checks performed deliberately.

Use issues for reproducible problems and proposals and pull requests for changes. Include the behavior and relevant validation rather than only a list of touched files.

Release the package

Only packages/cli is publishable; the workspace root is private. A release needs a matching package version and changelog, full verification, inspected tarball contents, and a smoke test of the exact tarball to be published.

The release guide is the authoritative maintainer procedure for npm authentication, trusted GitHub publishing, artifact verification, tags, and registry checks. Use it before publishing and never reuse a version that reached npm.
