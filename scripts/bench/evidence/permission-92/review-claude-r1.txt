## Findings

**1. Medium — `scripts/bench/permissions.py:78-86`: restoration depends on `finally`, and the script has no signal handling.**
- Problem: the script rewrites tracked production source at line 68. SIGTERM (exit 143) terminates Python without running `finally`, so the mutated source stays. The same session did take a 143 on a neighbouring runner. `scripts/bench/run.py` handles SIGINT and SIGTERM, per the bench README.
- Impact: a killed run leaves a "candidate" `private-storage.ts` that could be committed.
- Fix: install a SIGTERM handler that raises, or add a pre-flight check that refuses to run on a dirty source file. Alternatively, build the candidate in a copied or worktree checkout and never touch the tracked file. Disclose the limit in the report if you leave it.

**2. Low — `permissions.py:78-86`: restoration asserts can hide the real failure.**
- `assert` statements inside `finally` replace any earlier exception, and `python -O` strips them.
- `restoration.json` hard-codes `true` booleans. It is only written after the asserts pass, so it is truthful today.
- Fix: compute the booleans from the comparisons and raise explicit errors. Keep the original exception chained.

**3. Low — `permissions.py:24-28`: there is no clean-tree check, and the file does not record the repository head's dirty state.**
- `candidate-diff` runs `git diff -- source`, which silently includes any prior local edit.
- `head.log` records the SHA but not `git status`.
- Fix: assert `git diff --quiet -- <source>` at the start and record `git status --porcelain`.

**4. Low — `permissions.py:64`: the script is single-use and brittle.**
- `candidate.count(before) == 1` fails as soon as `private-storage.ts` is reformatted, because the replacement strings are hard-coded.
- The file is generically named `permissions.py` for a rejected one-off. It also differs from `listing.py` in quote style and in having no shebang or `REPO` constant.
- The convention is acceptable, since `listing.py` is also an "#91 only" runner. The docstring already says "#92".
- Fix: say in the module docstring that it reproduces the experiment only against `52cdb70` and breaks when that file changes. Consider renaming it `permission-92.py`.

**5. Low — `packages/cli/src/private-storage.test.ts:38-71`: the replacement test can pass without exercising anything.**
- If the `fs.lstat` mock stops intercepting, the target is already private. This would happen if the module moved to ESM named imports, which bind at link time. The `0600`/`0700` assertion at line 69 would then pass vacuously.
- The removal test would fail loudly in that case, and baseline did prove the mock fires today. The gap is therefore latent.
- Fix: count interceptions in each test and `assert.equal(count, 1)`.

**6. Low — `private-storage.test.ts:12-71`: duplicated setup and no explanatory comment.**
- Fixture creation (lines 16–20 and 42–46) and the `lstat` interceptor (lines 23–32 and 49–66) are repeated.
- Nothing says why the test hooks `lstat` at that exact point.
- Fix: extract one helper such as `mutateAfterInspection(t, target, mutate)`. Add a short comment: it pins "path-based chmod acts on the object present at chmod time" as a characterization test, so a future descriptor-based design must change it deliberately.

**7. Low — `private-storage.test.ts:2` and `permission-92.md:30-37`: the tests encode the implementation, not only the contract.**
- A descriptor-based hardening would legitimately fail the removal test, because `fchmod` on an open fd succeeds after unlink.
- The report calls these "observable interleavings" and defers descriptor design as out of scope, which is consistent. State outright that these are characterization tests tied to the path-based implementation.

- Slot and review-process mentions at lines 15, 135–136 and 141–147 are process notes, not evidence.
